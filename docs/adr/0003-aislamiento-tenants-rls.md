# ADR 0003 · Aislamiento de tenants con RLS

- **Estado:** aceptada (2026-11-04)
- **Contexto:** SP1 · T4, `apps/api` + Postgres 17 (`infra/docker-compose.yml`). Ampliada en SP2 · T1 (2026-11-05): `tenants`, FK compuestas, `monaco_auth` y las funciones de autenticación (puntos 6 a 9).

## Contexto

La plataforma es multi-negocio: varios tenants comparten la misma API y la misma base de datos. Un `WHERE tenant_id = ?` olvidado en un repositorio basta para filtrar datos de otro negocio. Queremos que la base de datos sea una **segunda barrera** (la primera sigue siendo la API: permiso + punto en cada caso de uso, docs/20) y que esa barrera no dependa de que cada query esté bien escrita.

## Decisión

1. **Esquema compartido + columna `tenant_id uuid not null`** en cada tabla de un tenant. Nada de una base o un esquema por tenant.
2. **Row-Level Security en cada tabla de tenant**, con una política única (`tenantIsolationPolicy()` en `apps/api/src/infrastructure/db/schema/tenancy.ts`):

   ```sql
   CREATE POLICY <tabla>_tenant_isolation ON <tabla> AS PERMISSIVE FOR ALL TO public
     USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
     WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
   ALTER TABLE <tabla> FORCE ROW LEVEL SECURITY;
   ```

   - `USING` filtra lecturas, `UPDATE` y `DELETE`; `WITH CHECK` rechaza escribir (o mover con `UPDATE`) una fila de otro tenant.
   - **Sin tenant no se ve nada (en vez de error).** `current_setting(..., true)` devuelve `NULL` si la variable nunca se definió y `''` si una transacción anterior de la misma conexión del pool la definió con alcance local; `NULLIF` convierte ambos casos en `NULL` y `tenant_id = NULL` nunca es verdadero. Se eligió así porque un error (`unrecognized configuration parameter`, o `''::uuid` inválido) dependería del historial de la conexión y sería intermitente; "cero filas" es determinista y sigue siendo seguro. El precio: un olvido de `withTenant` se ve como "no hay datos" y no como excepción, así que los tests de cada repositorio deben comprobar que encuentran datos.
   - **`FORCE`** hace que la política aplique también al dueño de la tabla (`monaco_owner`). drizzle-kit genera el `ENABLE ROW LEVEL SECURITY` y la política a partir del esquema, pero no modela `FORCE`: va en una migración custom (`pnpm --filter api db:generate --custom`, ver `drizzle/0004_iam_rls_grants_auth_functions.sql`). `src/infrastructure/db/__tests__/schema.test.ts` comprueba que cada tabla del esquema tenga `tenant_id uuid not null` y la política; el `FORCE` lo verifican los tests de integración (T5).
3. **Alcance por transacción:** `withTenant(db, tenantId, fn)` (`src/infrastructure/db/with-tenant.ts`) valida que `tenantId` sea un UUID, abre una transacción y ejecuta `select set_config('app.tenant_id', $1, true)` con el tenant como **parámetro** (nunca interpolado) antes de `fn(tx)`. El `true` hace la variable local a la transacción: desaparece en commit o rollback, así no pasa a otra petición que reciba la misma conexión del pool. Todo acceso a tablas de tenant debe hacerse con el `tx` recibido. `with-tenant.ts` es el único archivo de `apps/api/src` que puede contener `set_config(` o `SET app.` (lo vigila `src/infrastructure/db/__tests__/tenancy-guards.test.ts`): un `SET` de sesión o un `set_config(..., false)` persiste en la conexión del pool y la siguiente petición heredaría el tenant, saltándose el aislamiento.
4. **Roles separados** (`infra/postgres/init.sql`):
   - `monaco_owner`: dueño de la base, del esquema `public` y de las tablas; corre las migraciones (`DATABASE_MIGRATION_URL`, solo drizzle-kit). Sin `SUPERUSER` ni `BYPASSRLS`.
   - `monaco_app`: el rol con el que la API se conecta en runtime (`DATABASE_URL`). Sin `SUPERUSER`, `BYPASSRLS`, `CREATEDB` ni `CREATEROLE`; `NOINHERIT`. Solo `CONNECT`, `USAGE` en `public` y, mediante `ALTER DEFAULT PRIVILEGES FOR ROLE monaco_owner`, `SELECT/INSERT/UPDATE/DELETE` en las tablas y `USAGE/SELECT` en las secuencias que creen las migraciones. No tiene `TRUNCATE` (no está sujeto a RLS), no puede crear objetos ni leer el esquema `drizzle` de migraciones.
   - `monaco_auth` (SP2, `NOLOGIN BYPASSRLS`): dueño de las funciones de autenticación previas al tenant (punto 8).
   - `postgres` (superusuario) solo ejecuta `init.sql`: al crear el volumen y, como es idempotente, otra vez en una base creada antes de un cambio de roles. Las contraseñas de Compose y `.env.example` son solo de desarrollo; los roles de producción se crean en SP4.
5. **Un solo pool** (`DatabaseModule`, global): `pg.Pool` perezoso (no conecta hasta la primera query, así `pnpm openapi:generate` y los tests unitarios no tocan la DB), `connectionTimeoutMillis` de 5 s, listener de `error` para clientes inactivos y `pool.end()` en `onApplicationShutdown`.

6. **`tenants` es la excepción explícita**: no tiene `tenant_id` porque la fila *es* el tenant. Tiene RLS + `FORCE` y su política (`tenantRowPolicy()`) compara `id = app.tenant_id`, así que dentro de `withTenant` la API solo ve su propio tenant y puede bloquearlo (`SELECT ... FOR UPDATE`, el mutex del invariante de owner de SP2). Los guards (`schema.test.ts` y `test/integration/schema-guards.test.ts`) la tratan por nombre y exigen esa política exacta; para las demás tablas el chequeo de `tenant_id` no cambió.
7. **FK compuestas con `tenant_id`.** RLS no valida la fila referenciada y los chequeos de FK ignoran RLS: con una FK simple, el tenant A podría apuntar a un `role_id` del tenant B, y la diferencia entre éxito y error 23503 revelaría qué ids existen en otros tenants. Por eso cada tabla padre lleva `UNIQUE (id, tenant_id)` y cada referencia entre filas de tenant es `(x_id, tenant_id) → padre (id, tenant_id)`: `role_permissions`, `role_assignments` (usuario y rol), `role_assignment_locations` (asignación y punto), `devices`, `refresh_tokens` y `audit_events.actor_user_id`. Con eso, un id de otro tenant y un id inexistente dan el mismo error. Lo verifican `schema.test.ts` (toda FK hacia una tabla de tenant incluye `tenant_id`) y `test/integration/iam-schema.test.ts`.
8. **Puertas previas al tenant: `auth_lookup_user(email)` y `auth_lookup_refresh(token_hash)`.** Antes del login (y del refresh) no hay tenant y `FORCE` oculta todas las filas, incluso al owner. En lugar de relajar la política o dar `BYPASSRLS` a `monaco_owner`/`monaco_app` (prohibido, y un test lo verifica), hay dos funciones `SECURITY DEFINER` (`drizzle/0004_iam_rls_grants_auth_functions.sql`):
   - Son de **`monaco_auth`**, un rol `NOLOGIN BYPASSRLS NOINHERIT` que solo tiene `USAGE` en `public` y `SELECT` sobre las columnas que devuelven las funciones (no sobre la tabla entera).
   - `SET search_path = pg_catalog, public`, nombres calificados, igualdad exacta (`email = $1::citext`, `token_hash = $1`; nunca `LIKE`), `STRICT` y `LIMIT 1` sobre una clave única: como mucho una fila. `auth_lookup_user` devuelve `id`, `tenant_id`, `password_hash` y `status`; `auth_lookup_refresh`, `tenant_id`, `device_id`, `family_id` y el estado (`expires_at`, `absolute_expires_at`, `rotated_at`, `revoked_at`). Después todo sigue dentro de `withTenant`.
   - `REVOKE ALL ... FROM PUBLIC` y `GRANT EXECUTE ... TO monaco_app`: ni siquiera `monaco_owner` puede ejecutarlas.
   - **Cómo se crean sin superusuario en las migraciones.** Crear un rol `BYPASSRLS` exige superusuario y `monaco_owner` es `NOCREATEROLE`, así que el rol lo crea `init.sql` (ahora idempotente) y la migración `0002_iam_prerequisites.sql` solo comprueba que exista con los atributos correctos, y si no, falla con un mensaje que indica volver a correr `init.sql` como superusuario. `init.sql` también hace `GRANT monaco_auth TO monaco_owner WITH INHERIT FALSE, SET TRUE`: el owner no hereda nada de `monaco_auth`, pero puede hacer `SET ROLE monaco_auth`, que es lo que necesita la migración para crear las funciones con ese dueño. La migración le da a `monaco_auth` `CREATE` en `public` solo mientras crea las funciones y se lo quita al terminar. Se eligió esta opción frente a crear las funciones en `init.sql` como superusuario porque así las funciones quedan versionadas con el esquema que leen y se actualizan con una migración más, y no le da al owner un poder nuevo: como dueño de las tablas ya podía desactivar RLS. Lo que importa es que `monaco_app` no sea miembro de `monaco_auth`, y eso lo verifican la migración y los tests.
   - **Riesgos aceptados:** ante una inyección SQL en la API, `monaco_app` podría pedir el hash de contraseña de un email que ya conoce, o el estado de un refresh token del que ya tiene el hash (es decir, el token). Las funciones no permiten listar ni buscar por patrón. Cualquier cambio en ellas pasa por los tests dedicados de `iam-schema.test.ts` (dueño, `EXECUTE`, columnas, coincidencia exacta, una fila, `search_path`).
9. **Privilegios de `monaco_app` por tabla** (en la misma migración, sobre los permisos por defecto): `audit_events` solo `INSERT` y `SELECT` (append-only); `tenants` solo `SELECT` y `UPDATE` (los crea la CLI como owner); `locations`, `users`, `devices` y `refresh_tokens` sin `DELETE` (se archivan, desactivan o revocan); `roles`, `role_permissions`, `role_assignments` y `role_assignment_locations` con DML completo. `schema-guards.test.ts` fija esta matriz.
10. **Ids UUIDv7 generados en la aplicación** (`src/infrastructure/db/uuidv7.ts`, `primaryId()` en el esquema Drizzle). Postgres 17 no tiene `uuidv7()` nativo (llega en 18) y una función PL/pgSQL como default sería más lenta y luego divergiría de la nativa; por eso las columnas `id` no tienen default y los inserts en SQL crudo (seeds, tests) deben pasar el id. Al migrar a Postgres 18 se puede agregar `DEFAULT uuidv7()`.

## Alternativas descartadas

- **Una base o un esquema por tenant:** aislamiento más fuerte, pero migraciones N veces, pool por tenant y reportes cruzados (demo, soporte) complicados. No compensa para negocios pequeños.
- **Solo filtros en la API (sin RLS):** un único descuido filtra datos; no hay segunda barrera.
- **`SET app.tenant_id` de sesión (sin `LOCAL`):** con un pool, la variable queda en la conexión y la hereda la siguiente petición. Exige un `RESET` que se puede saltar si hay una excepción.
- **`current_setting('app.tenant_id')` sin `missing_ok`:** falla si la variable no existe, pero no si quedó en `''` de una transacción anterior (ahí falla el cast). Comportamiento intermitente según la conexión; ver punto 2.
- **Conectar la API como dueño de las tablas sin `FORCE`:** el dueño se salta RLS y los tests pasarían en falso.
- **Seguridad solo por `to monaco_app` en la política:** con `to public` + `FORCE` la política alcanza también al dueño y a roles futuros.
- **Login con `BYPASSRLS` en `monaco_app` o una política "sin tenant" para `users`:** cualquier consulta de la API (o una inyección) leería todos los tenants. Las funciones `SECURITY DEFINER` limitan esa puerta a una fila y unas pocas columnas.
- **`GRANT monaco_auth TO monaco_owner` con `INHERIT`:** el owner tendría implícitamente los permisos de `monaco_auth`; con `INHERIT FALSE` solo los usa quien hace `SET ROLE` explícito, que es la migración.
- **Crear las funciones en `init.sql` (superusuario):** evita la membresía, pero saca del versionado de migraciones unas funciones que dependen del esquema y exige correr SQL de superusuario en cada cambio.

## Consecuencias

- Una base creada antes de SP2 (volumen de SP1) necesita volver a correr `infra/postgres/init.sql` como superusuario antes de `db:migrate` (ver el encabezado del archivo); si no, la migración `0002` falla sin aplicar nada.
- Cada referencia nueva entre tablas de tenant es una FK compuesta con `tenant_id`, y la tabla padre lleva `UNIQUE (id, tenant_id)`.
- Cada tabla nueva de un tenant necesita: `tenant_id uuid not null` (con índice), `tenantIsolationPolicy('<tabla>')` en su definición Drizzle y `ALTER TABLE ... FORCE ROW LEVEL SECURITY` en su migración. El test de esquema falla si falta la política y `tenancy-guards.test.ts` falla si ninguna migración tiene el `FORCE` de una tabla con política.
- Cargas o backfills de datos de varios tenants no pueden hacerse como `monaco_owner` sin fijar el tenant (también está sujeto a RLS): se hacen tenant por tenant con `withTenant` o, en mantenimiento, con un rol administrativo explícito.
- RLS no protege contra un bug que llame a `withTenant` con el tenant equivocado: el tenant debe salir siempre del contexto autenticado (SP2), nunca del cuerpo de la petición.
- Las políticas evalúan `current_setting` por fila; con el índice en `tenant_id` el costo es bajo, pero las queries pesadas de reportes se revisan con `EXPLAIN` en SP4.
